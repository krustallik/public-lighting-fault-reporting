## 1. Executive synopsis

- Current code uses Leaflet raster tiles from the canonical OSM Standard URL. They are enabled by default only in Vite development; a production build needs `VITE_PUBLIC_MAP_TILES_APPROVED=true`. That flag does not change the URL to a commercial provider. The production tile host/account, deployment environment, and actual live runtime settings are **not determined from the repository**.
- Device geolocation is attempted once when the map component mounts. A distinct device marker can be rendered, while the recenter button is separately gated and does not select a report target. Geolocation remains in browser memory in this flow. The map entry behavior is owner-approved; the additional production recenter gate and provider/privacy notice still need closure.
- `POST /api/reports/address-suggestion` is mounted, but the production singleton has no provider and returns disabled. Fake providers are injectable in non-production tests. Existing queue/cache settings are constructor options, not environment configuration. A separate legacy Nominatim path exists for inventory/light-point address enrichment when `NOMINATIM_AUTO_GEOCODE=true`; it is not the report-address adapter.
- `classifyServiceAreaPoint()` accepts an injected Polygon/MultiPolygon and returns `inside`, `boundary`, or `outside` plus invalid/unconfigured states. No Košice polygon is configured and the classifier is not used by a report route. Current checks cover ring structure and coordinate ranges, not complete OGC topology.
- **Tile recommendation for owner review:** CARTO Basemaps, conditional on the owner accepting its terms, the 1M/month commercial-free threshold, no guaranteed availability, attribution, and its documented 30-day US request-log processing. MapTiler Cloud is a practical fallback; a production-capable subscription is required, and its lower plan does not publish an SLA. Neither is selected here.
- **Address recommendation for owner review:** Geoapify is the best fit for both reverse lookup and optional typed-address autocomplete. Use of its Free plan in production is stated broadly on its pricing page but qualified by v5 Terms (“with some limitations” and contact for details). Obtain provider confirmation for the actual city/public-service use and qualified privacy/legal approval first. HERE is a fallback only if its “Asset Management” exclusion is resolved in writing for this application. No provider is enabled.
- Production activation should be split into: (1) tiles/recenter after tile-provider and privacy gates; (2) service-area enforcement after boundary selection and validated geometry; (3) reverse lookup and optional typed autocomplete after provider, data-transfer, notice, and admission gates. Boundary and tile work can be planned independently. No DB migration or duplicate-history design is in scope.

## 6. Geometry validation and service-area hardening

The current classifier is **not sufficient by itself for production activation**. It structurally checks Polygon/MultiPolygon, rings of at least four positions, closed first/last coordinate, WGS84 ranges, holes during point classification, and a hand-coded ray cast. It does not establish valid polygon topology: self-intersections, zero-area rings, nested/outside holes, overlapping MultiPolygon components, invalid rings and other OGC validity conditions are not comprehensively checked. The current unit test file covers a simple square, boundary/inside/outside, invalid coordinates, unconfigured/malformed boundary, and one hole; it does not demonstrate comprehensive MultiPolygon/topology behavior. `EDGE_EPSILON=1e-10` operates on degree coordinates/cross products and is not a documented meter tolerance.

**Before enabling enforcement:**

1. Use an official source file and deterministic transform. Validate type, coordinate dimensions/ranges, ring closure/orientation requirements, no empty/degenerate/zero-area ring, no self-crossing, valid hole containment/non-crossing, no invalid MultiPolygon overlap/touch per selected policy, and no unexpected geometry collection. Fail the import/build on any issue; do not auto-repair silently.
2. Validate once during checked geometry generation/build/startup; store source metadata/hash beside the generated immutable geometry. Runtime should only parse the verified artifact and classify each request. Also validate the request coordinate in the authoritative backend report path; client validation is user feedback, not security enforcement.
3. Evaluate an established OGC geometry implementation rather than expanding the custom predicate. Candidate JSTS is a JavaScript port of JTS supporting Simple Features/GeoJSON; PostGIS/GEOS has `ST_IsValid` and `ST_Covers` semantics but requires a separate PostGIS/database decision. No dependency/database change is authorized now. Confirm current maintenance, license, bundle/runtime impact and numeric behavior before selection. [JSTS project](https://github.com/bjornharrtell/jsts), [PostGIS `ST_IsValid`](https://postgis.net/docs/ST_IsValid.html), [PostGIS `ST_Covers`](https://www.postgis.net/docs/manual-3.5/en/ST_Covers.html).
4. Avoid a guessed degree epsilon. Prefer a robust topological predicate for exact inside/boundary/outside and no implicit buffer. If owner requests tolerance, define it in meters in an appropriate projected CRS and test the transformed data and points around every edge.
5. Keep the known/custom/device target distinction. Show localized “outside this service area” feedback on the client and reject again on the backend report path. Test the manual fallback and a boundary error without sending any provider or AUSEMIO request.

The existing generic unit tests are a useful seam, not proof that an authentic Košice polygon is valid. No geometry artifact, hash, runtime DB boundary, or enforcement route is present at the inspected SHA.

## 9. Proposed admission, cache and anonymous-caller policy

Values below are a conservative starting proposal for a single backend process and low expected thesis/pre-production traffic. They are not current configuration and need O5/O11 owner approval plus provider confirmation. Geoapify currently publishes a Free quota of 3,000 credits/day and up to 5 requests/second; the provider says quota/rate handling is soft and its terms allow suspension/charges in some circumstances. Therefore the internal limits below are not a guarantee against provider-account overage, especially after process restart or if another system shares the account.

| Setting | Initial proposal | Rationale / caveat |
|---|---:|---|
| Shared address `maxActive` | 1 | Serializes current one-process requests and bounds sockets/memory. Reverse and autocomplete share one provider/account rate gate. |
| Shared `maxPending` | 8 | Small fixed queue; memory bounded. FIFO is service order only, not per-caller fairness. |
| `minStartIntervalMs` | 250 ms (4 dispatches/sec) | Below Geoapify’s published 5 requests/sec plan limit, leaving 1 request/sec headroom for clock/concurrent effects. Tile calls use separate CARTO account/provider to avoid sharing this budget. |
| `timeoutMs` | 3,000 ms | Keep UI fallback timely; abort upstream where supported. An adapter that ignores abort must continue occupying its active slot until it settles, as the current service already does. |
| `queueExpiryMs` | **2,000 ms — engineering proposal only; not approved for production** | With `maxActive=1` and a 3-second provider timeout, a queued request may expire while the active request is still executing. This may be acceptable for an optional address suggestion with manual fallback, but the final expiry value requires owner approval and synthetic UX validation. Expired work must make zero upstream calls. |
| In-memory cache | 256 entries; 5 minutes | Bounded and ephemeral; no DB/disk. Geoapify states results can be cached, but the app’s minimization policy still prefers short TTL. Use a provider/operation/language key plus exact normalized coordinates for reverse; do not round coordinates into a different point. For typed queries use normalized query + language/country key, store only the displayed suggestion payload. No raw key/URL/query logging. |
| In-flight coalescing | Exact canonical input key | Reverse: provider ID + operation + language + exact normalized full-precision lat/lon. Autocomplete: provider ID + operation + language + country + normalized query. No spatial rounding that could return an adjacent-address result. In-memory only. |
| App dispatch budget | 1,000 upstream address requests per UTC day per process | At one credit/request this is one third of Geoapify’s published 3,000/day Free quota, leaving headroom. Count every dispatch including provider errors; do not count cache/coalescing hits or rejected/expired work. **Restart resets this in-memory budget**, and provider Free quota is soft; an owner must decide whether that is acceptable or require a provider-enforced hard cap/operational alert before production. Do not call this a hard daily guarantee. |
| Rejection | HTTP 429 with stable generic codes (`admission_rejected`, `queue_full`, `queue_expired`, `application_cap`) | UI explains temporary unavailability and offers manual input; do not include provider response, coordinates or query. No automatic retry. Invalid input remains 400; disabled 503; provider timeout 504; provider failure 502. |
| Autocomplete input | min 3 code points; debounce 350 ms; max 5 results | Reduces cost and overly broad results while keeping suggestions usable. Current free plan cost is 1 credit per API request; rate is shared with reverse calls. Values need owner/UX/provider confirmation. |

Pre-provider rejection tests must assert both **zero fake-provider calls** and **zero budget consumption** for invalid request, admission reject, queue full, queue expiry before provider start, application cap, disabled provider, and any future pre-provider overload. Provider timeout after dispatch is a provider call and counts against dispatch budget. Queue expiry after dispatch is not an admission case; test timeout/abort separately.

**Anonymous caller policy proposal:** keep the route product-scoped, same-origin, JSON-bounded and not a general geocoder API. Use global bounded queue + application budget + client debounce/cancellation, generic 429 and manual fallback. Do not add CAPTCHA or mandatory auth without evidence. Do not trust arbitrary `X-Forwarded-For` for per-IP controls. If a known reverse proxy is introduced, an edge rate limit can be evaluated with explicit trusted-proxy configuration, spoofing tests, privacy notice/retention, and NAT fairness analysis. Per-IP fairness remains unresolved; IP controls can penalize shared networks and expose identifiers. Global FIFO does not promise caller fairness. If backend count grows above one, per-process queue/cache/budget/coalescing split across processes; redesign to a shared provider proxy/atomic quota/cache or provider-level quota before scaling. No Redis is proposed for this current topology.

## 10. Logging, secrets, and privacy-by-design

**Allowed operational telemetry proposal:** aggregate counts by operation/result class; accepted/rejected/coalesced/cache-hit totals; queue depth and active count; latency buckets; provider status/error class; budget remaining as a coarse counter. Keep dimensions low cardinality. Do not emit coordinate, exact address, typed query, phone/email, free text, file metadata, IP, fingerprint, raw request body, API key, or full upstream URL. Strip provider URLs/query strings and response bodies from exceptions before logging. Do not forward citizen IP to the address provider.

Current `/address-suggestion` uses POST JSON (coordinates are not in the local URL), and the route/service produce safe generic error bodies; the production error handler does not echo the body. This is not proof about reverse-proxy, host, APM, or vendor logs. The legacy Nominatim adapter constructs an outbound GET URL containing exact coordinates. Before using any live adapter, add tests around app error logging and validate actual hosting/proxy/APM settings; no evidence of such production log configuration is in the repository.

**Configuration proposal:**

- Separate tile and address provider settings. Tile key is a browser-visible public key: domain/referrer restrict it, limit it to tile APIs, and monitor provider usage; never treat it as a secret or commit it. Keep the address-provider key server-side in secret storage/environment because exact address/coordinate requests must pass through backend adapter. Never put address keys in `VITE_*` variables.
- Default provider disabled. Require explicit provider ID + HTTPS endpoint + key + style/attribution/plan confirmation before service construction. Fail closed on missing/malformed config; do not fall back to OSM, Nominatim, or another provider implicitly.
- Preserve a fake provider injection for tests/dev. Do not make development’s fake key or provider config usable in production. Vite tile config is baked at build time; production `VITE_*` variables must be set by the build/deployment, not assumed to be runtime toggles.
- Proposed names only (none currently exist): `MAP_TILE_PROVIDER`, `VITE_PUBLIC_MAP_TILES_APPROVED`, a public/domain-restricted `VITE_MAP_TILE_KEY`, `VITE_ALLOW_DEVICE_MAP_RECENTER`, `REPORT_ADDRESS_PROVIDER`, `REPORT_ADDRESS_PROVIDER_BASE_URL`, server-only `REPORT_ADDRESS_API_KEY`, and explicit admission settings. Do not add them until owner/provider decisions settle.
- Keep `NOMINATIM_*` scoped to legacy inventory geocoding; do not reuse it as the report-address provider or for autocomplete. `.env.example` currently has `NOMINATIM_AUTO_GEOCODE=false`; no report-provider key/config is present.
