## 1. Purpose and boundaries

Research a mobile-first way to start and complete a public-lighting fault report using either an existing lighting point or a manually selected point, optionally assisted by browser geolocation and reverse geocoding. Define alternatives and tests to write after owner decisions; do not implement any behavior in this checkpoint.

Hard boundaries carried forward:

- Product scope is service `2` / VO only. Service `16` / CSS remains **OUT OF PRODUCT SCOPE**.
- The local result remains simulated. No external AUSEMIO fallback, submit, write, or live integration is authorized.
- Do not add durable storage or logs for citizen email, phone, photos, free text, or precise location/report payload without owner approval and, separately, any qualified legal review required for the actual data flow.
- Browser geolocation must remain optional. The accepted roadmap requirement is an explicit user action plus browser permission; denial/unavailability must leave a usable alternative.
- Current target lifecycle and user-edit precedence remain in force until an explicit owner decision changes them.

## 3. Mobile-first UX alternatives

All options must preserve optional geolocation and a manual path. They are alternatives, not accepted designs.

| Option | User path | Benefits | Trade-offs / decision needed |
|---|---|---|---|
| **A — map-first, retain current entry point** | Open map; choose an inventory light point or a custom map point; optionally activate “use my location”; confirm/adjust the target; continue to the existing report steps. | Smallest conceptual change to current product; target selection is visible before the form; direct inventory-point path remains. | The map remains the first obstacle if tiles/data fail; keyboard users need a non-pointer way to reach a target; map area and controls can dominate a small viewport. Decide initial map extent, fallback screen, and whether geolocation centers the map or proposes the report target. |
| **B — report-first with optional location panel** | Begin with a short report entry screen; choose a known point, use the map, explicitly request current location, or continue with manual locality/address; reveal issue/contact fields as needed. | Avoids making a functioning map a prerequisite; manual route is discoverable; location can remain optional. | Requires a new target-selection/search interaction and changes the existing `/map` landing flow; decide how a selected inventory ID or custom point transitions into the form. |
| **C — guided location-first steps** | Step 1: choose source/target and confirm location. Step 2: describe fault. Step 3: contact/attachments and review, if owner wants a separate review. | Makes target source and confidence explicit; separates location recovery from report details; straightforward state-specific progress announcements. | More steps and navigation; repeats or replaces the current two-step form; can increase abandonment on mobile. Decide step count, where phone/email/attachments belong, and whether a separate final review is required. |

### Shared interaction alternatives to decide

1. **Selected lighting point:** either show current inventory label/address and a clear confirmation/change control, or open the report form as today with an implicit target context. Do not equate that asset location with the reporter's device location.
2. **No selected point:** the accepted requirement allows map choice and a fallback. Alternatives are map pin selection with a manual locality/address path, or address/locality first with an optional map correction. Decide which source identifies the report target.
3. **Geolocation:** proposed default is a visible user-activated, one-shot request. It may center the map and display the reported accuracy radius, or preselect a provisional marker requiring confirmation. Do not use continuous `watchPosition()` for a one-time report unless an owner provides a distinct need. Exact trigger placement, high-accuracy flag, maximum wait, freshness, accuracy messaging and what happens to an existing target are **OWNER DECISION REQUIRED**.
4. **Reverse geocoding:** alternatives are a) one lookup after explicit map-target confirmation, b) a separate “suggest address” action, or c) no remote reverse lookup until provider/privacy approval, using locality/manual entry only. Never request on pan, drag, typing, or autocomplete. Decide attribution placement and whether the address is just a suggestion.
5. **Address edit:** show the returned address as editable suggestion with explicit accept/replace controls, or keep the current locality selector authoritative and use the address only as a hint. In either case, do not silently overwrite a user-edited field.
6. **Progressive disclosure:** retain 2 steps, split location from issue/contact, or use an inline location panel. Decide final count and content distribution after a mobile prototype/accessibility review.

## 4. Geolocation semantics and proposed client state model

### Confirmed external behavior

- Browser geolocation is secure-context-only and requires explicit browser permission. The approved product requirement adds a separate explicit in-product action before requesting it.
- A position may be derived from different platform signals and is not guaranteed to be the device's true physical position. The API supplies an accuracy radius and acquisition timestamp; the browser may return a cached position depending on options.
- `PositionOptions.maximumAge` expresses the maximum age, in milliseconds, of a cached position the application is willing to accept; if no sufficiently recent cached position is available, the user agent acquires a position. The default is `0`; no product value is selected here. See the canonical privacy note for the normative API semantics and their limits.
- Permission denial, position unavailable, and timeout are distinct errors. The acquisition timeout does not necessarily bound the time the user spends deciding on the permission prompt.
- High-accuracy requests can cost additional time/power and may be ignored. No particular options value is selected here.

Source and date: [W3C Geolocation CR Snapshot (2026-03-26)](https://www.w3.org/TR/geolocation/), checked 2026-10-05; details and limits in the [canonical security/privacy note](../security-privacy/p2c-geolocation-privacy-evidence.md).

### Proposed state model (not approved)

`idle → requesting permission/location → position acquired → provisional map center/marker → user confirms or corrects → address suggestion (only if provider/privacy gate is open) → confirmed report target`

Failure states return to the same usable manual/map path:

- **permission denied / blocked by policy:** explain how to continue manually; do not repeatedly prompt or block reporting;
- **position unavailable / unsupported / insecure context:** retain map and manual entry; never mark the report target as missing solely for this reason;
- **timeout:** stop spinner, preserve any prior selection, offer manual map/address path and a user-controlled retry;
- **poor accuracy:** display the platform-provided accuracy in user language and require deliberate target confirmation/correction; threshold is an owner decision;
- **stale/out-of-order callback:** discard results for an old target or unmounted step; never replace an address/target after a later manual edit.

No location collection should start on page render, route navigation, map movement or form submission without the approved explicit action. The failure mapping and state machine require mock-controlled component/API tests before implementation.

## 5. Reverse-geocoding policy and current Nominatim design

### Current provider behavior in code

`backend/src/services/geocoding.service.ts::reverseGeocode` validates WGS84 bounds, checks a coordinate key rounded to 5 decimals, waits for the configured interval, then calls `{NOMINATIM_BASE_URL}/reverse` with `format=json`, the supplied `lat`/`lon`, `zoom=18`, `addressdetails=1`, `User-Agent`, and `Accept-Language` (default `sk`). It parses `display_name` or builds a short address from returned fields and caches a positive result. The public HTTP response exposes address, original query coordinates and literal source `nominatim` (`backend/src/types/geocoding.ts`). The raw provider `licence` field is not propagated.

The example config has a 1,100 ms interval. A single serial caller would wait at least that long between requests; this is not an application-wide guarantee. Concurrent callers race because each computes elapsed time and sleeps independently before setting `lastRequestAt`; an identical in-flight request also misses the cache until the first completes. Multiple backend processes have independent maps/timestamps. No timeout, abort, provider response schema validation, retry/backoff policy, negative-cache rule, or per-caller/API admission control is visible. Non-2xx upstream response maps to 502; network/JSON errors propagate through normal error handling. `geocodingController.reverse` forwards caught errors with `next(err)`; `backend/src/middleware/errorHandler.ts` calls `console.error(err)` unless the error is an `AppError` with status below 500. This establishes an application logging call for applicable errors, not the deployed log sink or whether an error contains query values.

The frontend geocode helper duplicates a 5-decimal page-memory cache. It is not used by current `frontend/src` consumers found in this inspection. Its light-point-specific helper calls a route absent from the currently mounted backend light-points router.

### Official policy evidence

The [OSMF public Nominatim policy](https://operations.osmfoundation.org/policies/nominatim/) was checked 2026-10-05. It confirms an absolute maximum of one request per second per application, with traffic from all users aggregated; identification via a valid application-identifying Referer or User-Agent; visible attribution; and caching/proxying where possible. User-triggered queries are allowed for a moderate population. The public service forbids client autocomplete/systematic query patterns and says not to submit personal/confidential data. Provider choice must also allow switching if requested. Policy is public-endpoint-specific and may change.

The [Nominatim Reverse API manual](https://nominatim.org/release-docs/latest/api/Reverse/) (latest manual identified as 5.3.2; checked 2026-10-05) says reverse lookup returns the closest suitable indexed OSM object, not an interpolated exact address. A displayed result must therefore be an editable suggestion with user confirmation; it cannot define the authoritative fault location or asset identity.

The configured default User-Agent is an app-like string, but `.env.example` and Compose defaults contain example/generic contact values. The actual deployment value and contactability are **UNKNOWN**. Confirm a real application-identifying contact before relying on public Nominatim. The code's `NOMINATIM_BASE_URL` allows endpoint configuration, but no runtime UI/provider switch or alternate provider adapter exists.

### Architecture alternatives

| Option | Shape | What it solves | Limits / approval |
|---|---|---|---|
| **A — current per-process cache and delay** | Current `Map`, 5-decimal key, sleep-based minimum interval in every caller; no public-route admission control. | Almost no additional infrastructure; completed repeat calls in one process may avoid an upstream request. | Not concurrency-safe or aggregate across instances; no in-flight dedupe/TTL/bound/timeout; retention of query keys until process exit; does not meet an application-wide quota guarantee under concurrent callers. It also does not define who may invoke the endpoint, a bounded backlog, overload response, or fairness. |
| **B — one in-process provider gateway with owner-defined admission contract** | Candidate shape: all geocoder calls route through one service-owned gateway with an owner-selected application-boundary admission policy, bounded backlog, provider-slot coordination and duplicate handling. Exact policy/values remain open under O11; no queue size, status, caller identity rule, or rate value is selected here. | Can coordinate routes and inventory jobs within one active process; can be exercised through fake transport and contract tests. | Only coordinates one process. It does not satisfy a multi-instance provider-wide limit without shared coordination. Admission, queue/backpressure, caller fairness, cache and privacy choices remain owner decisions. |
| **C — shared multi-instance coordinator** | Candidate shape: a shared gateway/worker or shared coordinator for admission, bounded queue, provider-slot scheduling and any shared duplicate/cache behavior across all API replicas. Exact contract/values remain open under O5/O11. | Could apply one chosen admission and upstream policy across replicas and background jobs. | Adds operational service, failure modes, network responsibility and potentially shared storage of query keys/results. **No architecture option is recommended or selected.** O5 (provider and topology) and O11 (public endpoint admission/abuse contract) are separate gates; O6 (product/provider/privacy decision about location transfer) is a separate owner gate; O12 records qualified legal review as a distinct prerequisite where applicable. Options B and C remain conditional technical candidates only. Until owner-selected caller scope, anonymity status, admission/rate policy, bounded backlog and overload contract exist, do not create dependent acceptance criteria or implement reverse-geocode exposure. A decision to keep the reverse lookup out of product flows is also an available product alternative; current code exposure alone is not approval for a user-facing or general public API.

### Proposed data minimization boundary

- Keep device location, accuracy and timestamp in client memory only for the active location-selection task unless the owner approves something else.
- Send a coordinate to the backend only after the user confirms the target and only if a geocoder/provider is approved. Show that an external lookup will receive coordinates before sending them if it is external.
- Treat returned street/locality/address as a suggestion; user confirmation and manual correction are required. Keep inventory asset identity separate from address text.
- Do not persist, log or add to the existing report free text a citizen-derived exact location solely to simplify mapping. Current custom-map behavior does embed selected coordinates into the local-test detail text; preserving versus redesigning that behavior is an explicit owner decision because it is already tested.
- Prefer no per-report location telemetry. If reliability monitoring is approved, start with aggregate provider/outcome/cache/latency counters and document retention/access/deletion in the canonical privacy note before adding fields.
- The public Nominatim restriction and potential linkability of a fault location create unresolved provider and product/privacy gates under O5/O6. Any legal assessment is a separate O12 review. Do not call it with a citizen/device coordinate until the applicable provider, owner, and legal gates are resolved.

## 10. Risks and unknowns

- **Provider/privacy mismatch:** public Nominatim says not to submit personal/confidential data; a device-derived or report-linked coordinate may be linkable in context. O5/O6 provider and product/privacy decisions block that flow; any applicable legal assessment is the separate O12 gate.
- **Rate coordination and abuse/admission:** current 1,100 ms per-process sleep does not guarantee the public provider's aggregate cap under concurrency or multiple instances. The public reverse route has no code-level authentication/admission/rate middleware; arbitrary callers could consume provider capacity, race the delay or create unbounded pending work if a queue were added without a bound. Caller scope, fairness, bounded backlog and overload/rejection semantics are O11 owner decisions. No load result was generated in this research task.
- **Address correctness:** reverse lookup is nearest-indexed-object semantics. Incorrect street/locality suggestions can misdirect a report; user confirmation and correction matter.
- **Current location is not the fault location:** geolocation accuracy and reporter-to-asset distance are unknown; confirmation is mandatory in any chosen flow.
- **Cache retention:** existing in-memory caches are unbounded until process/page lifetime ends. No approved TTL, coordinate precision, or deletion policy exists for citizen use.
- **Public route exposure:** `/api/geocode/reverse` is mounted without route authentication, throttling or admission control in repository code. Whether it remains anonymous/public, is limited to a product flow, or serves a general API is unresolved under O11; deployment proxy controls and request logging are unknown.
- **Provider identification:** actual environment override/contact is unknown; example values are not evidence of a production contact.
- **Map failure/accessibility:** current report start depends on map/inventory fetch; a code-visible keyboard alternative or no-map fallback is not present in these map components. Actual Leaflet keyboard/screen-reader behavior must be tested, not assumed.
- **Third-party policy scope:** OSM tile terms are checked; CARTO policy, provider-side telemetry/retention and deployment-level privacy disclosures are unknown.
- **Product/trust boundary:** local report echoes test input and remains simulated. No future external acceptance, receipt, service status or report lifecycle can be inferred.
- **Legal applicability:** actual controller, processor, lawful basis, notice, retention, data-subject rights and impact-assessment obligations are **не визначено з репозиторію**. Consult qualified legal/privacy owner against current effective EU/Slovak sources.
