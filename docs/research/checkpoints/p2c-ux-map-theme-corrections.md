# P2c targeted UX and map-theme corrections

**Status:** Local implementation draft on `feature/p2c-implementation-draft`; not merged and not approved for production release. This checkpoint records the owner corrections and current implementation/research evidence for targeted independent re-audit. It does not supersede the accepted decisions or unresolved gates in [the P2c owner-decision plan](p2c-owner-decisions-implementation-plan.md).

**Evidence date:** 2026-10-06 (Europe/Bratislava). External pricing, terms, and provider policies can change; verify them again before provider selection or launch.

**Starting code head:** `08d58141831d04ebead4ff1e1d1d6cb89ed72e7b`.

## 1. Owner corrections recorded

- The native 928-value locality select is rejected. Public users must search the canonical VO locality list and explicitly select a canonical value. Search is local and must not contact a provider.
- Phone validation requires an explicit `+` country prefix; no country inference or prefix insertion. The current application rule is 8–15 digits after `+`, with the first digit non-zero.
- The full public map → confirmation → report form → result experience must switch between Slovak and English while retaining applicable target/form state.
- The sidebar-heavy map is rejected. The map is the dominant, fullscreen surface, with compact locale/theme/recenter controls, short guidance, an accessible collapsed known-point alternative, and a non-map continuation.
- Light and dark map appearance are required. The earlier unauthenticated CARTO dark tiles could show `API KEY REQUIRED`; this draft removes CARTO from the configured layer and uses one raster source with a tile-only CSS dark treatment.

These requirements apply to the service-2 VO product only. Service `16` / CSS remains out of product scope. No AUSEMIO page/request/write, DB/schema/migration change, provider-backed citizen lookup, or production report transport was added.

## 3. Tile-provider research (official sources checked 2026-10-06)

All remote tile requests can disclose requested `{z}/{x}/{y}` and therefore approximate viewport area, plus network metadata such as source IP and HTTP headers. This is distinct from sending an exact report/device coordinate to a geocoder. Development map use and user panning still make approximate map area visible to the chosen tile service; the code does not claim that no location information is sent.

**Client-side dark rendering of OSM:** CSS filtering only `.leaflet-tile` is technically demonstrated by the current UI; it leaves markers, controls and attribution outside the filter and creates no second tile provider/request. OSMF policy does not expressly answer whether transformed rendering is permitted. This is therefore an implementation inference, not a confirmed legal interpretation. Keep production approval gated pending owner/privacy/legal acceptance of both the tile source and presentation.

**Self-hosted/vector comparison:** Self-hosting can avoid a third-party tile request for each viewport but requires sourcing/licensing data, tile generation/hosting, styling, cache/update pipelines, availability monitoring, storage/backups and ongoing operations. This is an inference from the extra system boundary and is disproportionate to the current pre-production draft without an owner/operations decision. Vector rendering can enable native restyling but would add WebGL/style/SDK surface and potentially increase client complexity; no performance benchmark was run.

**Recommendation:** for this correction only, use the canonical OSM URL in development and apply the client-side raster filter for dark appearance; keep production tiles closed unless the explicit approval configuration is supplied after the owner selects a provider and reviews terms/privacy/usage. Keep device recenter separately gated. This is not a production provider selection or assurance of unlimited/free service. No provider key has been added or is required by the current OSM development URL.

## 4. Address suggestion provider research

Canonical locality search is always local and separate from exact/structured-address suggestions. The current product action is explicit and low-frequency; the existing backend boundary validates and forwards only to a provider when one is deliberately registered. The production report-address service remains disabled (503); tests use fake providers and synthetic coordinates. Any future hosted provider call must be a backend adapter, with no provider secret in browser code, explicit user trigger, debounce/minimum input/cancel/stale-response handling if an autocomplete interaction is later approved, and no automatic fallback chain. A provider result is an editable suggestion, not authoritative address or canonical locality. No external citizen address/coordinate was sent in this checkpoint.

## 6. Remaining owner gates and known limitations

- Production tile provider, budget/quota, key/authentication and restrictions, owner/legal/privacy approval, required attribution and retention/disclosure decisions remain open. The current production config defaults to no tiles. Recenter remains a separate flag and must not be activated silently.
- External exact-address suggestion remains disabled until provider selection, terms acceptance, privacy/legal review where required, and deployment secret/admission/notice decisions are approved. Geoapify is a candidate, not an accepted provider.
- Service-area enforcement still requires the existing O1–O12 boundary gate; no administrative polygon was invented or activated here.
- Service `16` / CSS remains out of product scope. Existing address suggestion is a local explicit UX seam and its success/result does not imply external validation.
- Local Windows E2E/process-egress evidence remains unavailable; gated CI is required. Visual review and automated tests do not establish WCAG conformance or native Safari/iOS behavior.
- The broader historical P2c record is retained in [Phase A](p2c-phase-a-implementation.md), [Phase B](p2c-phase-b-implementation.md), and [the owner-decision plan](p2c-owner-decisions-implementation-plan.md).
